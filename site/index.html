odflens

odflens is an offline accessibility auditor for OpenDocument files: text documents (.odt), spreadsheets (.ods), and presentations (.odp). It unzips the ODF package, parses the XML, and reports issues without rendering the document.

The package is written in TypeScript and runs on Bun, in a terminal or a CI job, with no LibreOffice or Java. It understands the ODF 1.2 and 1.3 namespaces and can emit text, JSON, or SARIF 2.1.0. odflens is MIT licensed, and it is not published to npm. Install it with the one-line script, or run it without installing.

OpenDocument accessibility tooling today

OpenDocument is required in much of EU and public-sector publishing under EN 301 549 and the Web Accessibility Directive, but there is almost no tooling that checks its accessibility.

AccessODF

The only ODF accessibility checker with a working release. It is a LibreOffice GUI extension written in Java, at version 0.1.0 Beta, with its last file dated 2011-11-08. It requires a desktop office suite and cannot run headless.

ODFBetter / ODF_Accessibility_Tester

Both are abandoned, with no maintained release and no way to run them in a CI pipeline.

openxml-audit

Validates OpenDocument conformance only, not accessibility.

OOXML tooling

office-accessibility-checker, readrite, and filecap cover OOXML and XLSX rather than ODF. None of them opens an .odt, .ods, or .odp package.

odflens fills that gap with an offline ODF accessibility auditor that runs from a CI job without LibreOffice or Java, using the same rule engine in the terminal and in the browser.

What odflens does

Runs offline

There is no network code. Files are parsed locally and never uploaded, so the tool works on air-gapped machines and in CI containers with egress blocked.

Namespace-aware parsing

Rules match namespaced keys (text:h, draw:frame, svg:title) so the result does not depend on the prefix LibreOffice chose.

Command-line interface

Audit files or directories, emit JSON or text, and set the failure threshold with --fail-on.

SARIF 2.1.0 output

Each issue becomes a SARIF result, so findings show up as annotations in GitHub code scanning, VS Code, and other SARIF-aware viewers.

Library API

Call audit(bytes, name) directly and get back { file, kind, issues, counts }.

Kind detection

Detects ODT, ODS, and ODP from the package mimetype, then falls back to the body element.

How it works

The audit runs in four stages.

  1. Open the package

    fflate unzips the ODF container; mimetype and META-INF/manifest.xml confirm what kind of document it is.

  2. Detect the kind

    ODT, ODS, or ODP is read from the package mimetype first, then from the body element as a fallback.

  3. Parse namespace-aware

    content.xml, styles.xml, and meta.xml are walked with a namespace-aware findAll, so prefix choice never changes the result.

  4. Report

    Rules produce issues with a code, severity, WCAG mapping, and location, emitted as text, JSON, or SARIF 2.1.0.

odflens pipeline 
.odt/.ods/.odp ──unzip (fflate)──▶ mimetype + META-INF/manifest.xml
                                  ├── kind detection (mimetype, then body element)
                                  └── content.xml / styles.xml / meta.xml
                                        └── namespace-aware findAll + rules
                                              └── JSON / text report

Rules

Rule codes, severities, and the WCAG success criteria they map to.
Code Severity WCAG Check
ODF-LANG-001error3.1.1No document language (office:language / fo:language)
ODF-TITLE-002error—No non-empty dc:title in meta.xml
ODF-ALT-003error1.1.1Image frame without svg:title or svg:desc
ODF-HEAD-004warning1.3.1Heading outline levels skip
ODF-HEAD-005warning1.3.1Body text but no headings
ODF-TBL-006error1.3.1Table with rows but no table:table-header-rows
ODF-LINK-007warning2.4.4Link whose text is a raw URL
ODF-IMG-008info1.1.1Image referenced over http(s)://

ODF-000 (info) is reported when the package is unreadable or has no content.xml. Audit exits 1 on error-severity issues by default; --fail-on warning|info|none changes the gate threshold.

Install

odflens is a Bun and TypeScript package. It is not published to npm. Install it with the one-line script, or run it without installing.

# One-line install (installs the `odflens` binary)
curl -fsSL https://raw.githubusercontent.com/srivtx/odflens/main/install.sh | sh

# Or run once, without installing
bunx github:srivtx/odflens report.odt

# Install globally
bun add -g github:srivtx/odflens
odflens report.odt

# Add to a project as a dev dependency
bun add -d github:srivtx/odflens

CLI and library usage

# Audit one or more files
odflens report.odt sheet.ods deck.odp

# A whole directory
odflens --dir docs/

# Machine-readable
odflens report.odt --json

# Emit SARIF for GitHub code scanning
odflens report.odt --sarif odflens.sarif

Or call it as a library:

import { audit } from "odflens";

const result = audit(bytes, "report.odt");
// { file, kind: "odt", issues, counts }

The CLI exits 1 on any error-severity issue and 0 otherwise.

SARIF and GitHub code scanning

odflens emits SARIF 2.1.0, so results show up as annotations in GitHub code scanning, VS Code, and any other SARIF-aware viewer. Each issue becomes a result with ruleId set to the ODF rule code and a level mapped from its severity.

- name: Audit ODF documents
  run: odflens --dir public/docs --sarif odflens.sarif

- name: Upload SARIF
  uses: github/codeql-action/upload-sarif@v3
  with:
    sarif_file: odflens.sarif

Use --fail-on to tune when the job itself fails (error by default): odflens --dir public/docs --sarif odflens.sarif --fail-on warning.

Limitations

odflens performs static XML checks and does not render or convert the document. ODS and ODP rule coverage is a subset of the ODT coverage. Remote images are flagged but never fetched, and there is no network code, so files are parsed locally and never uploaded.

FAQ

Does it need LibreOffice or Java?

No. odflens is pure TypeScript: it unzips the package with fflate and parses the XML directly, so it runs headless on any machine that has Bun, including CI containers without an office suite.

Are my documents uploaded anywhere?

No. There is no network code at all. The CLI parses files locally, and the browser playground uses the same bundle in-page, so nothing leaves your machine.

Which formats are covered?

ODT (text), ODS (spreadsheet), and ODP (presentation). Kind detection reads the package mimetype and falls back to the body element; ODS and ODP coverage is a subset of the ODT rule set.

How does it fit into CI?

Run odflens --dir public/docs --quiet as a gate, or emit SARIF with --sarif and upload it with github/codeql-action/upload-sarif. --fail-on warning|info|none controls the exit threshold.

Why not just use AccessODF?

AccessODF is a LibreOffice GUI extension in Java, at 0.1.0 Beta, last filed in 2011. It needs a desktop suite and cannot run headless, which makes it unusable as an automated gate.

Does it render or convert documents?

No. It is a static XML auditor: it checks structure, language, alt text, heading order, tables, and links, and reports issues. It never renders, converts, or fixes a file.
